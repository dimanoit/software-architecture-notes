## Основні терміни

| English term | Коротке пояснення |
|---|---|
| **Architecture characteristic** | Системна якість і критерій успіху: scalability, availability тощо |
| **Architecture decision** | Правило або constraint, що спрямовує implementation |
| **Architecture style** | Іменована базова topology системи |
| **Architecture vitality** | Актуальність архітектури в поточному business/technology context |
| **Architectural thinking** | Системне бачення впливу та trade-offs рішень |
| **Technical breadth** | Обізнаність у багатьох technologies та підходах |
| **Trade-off** | Виграш однієї властивості ціною іншої |
| **Modularity** | Логічний поділ системи на пов'язані частини |
| **Granularity** | Розмір цих частин |
| **Cohesion** | Наскільки elements усередині module належать разом |
| **Coupling** | Ступінь залежності між artifacts або modules |
| **Connascence** | Необхідність змінити один component разом з іншим |
| **Structural decay** | Поступова втрата задуманих architecture characteristics |
| **Fitness function** | Автоматизована перевірка архітектурної властивості або правила |

## Формули Chapter 3

Нижче - навчальні розрахунки з вигаданими числами. Формули описують структуру коду; вони не оцінюють швидкість виконання чи коректність бізнес-логіки.

### Abstractness

$$
A = \frac{m_a}{m_c + m_a}
$$

- $m_a$ - кількість абстрактних типів: interfaces та abstract classes;
- $m_c$ - кількість concrete classes;
- знаменник $m_c + m_a$ - загальна кількість цих типів у модулі;
- для непорожнього набору типів значення лежить від `0` до `1`.

**Рахуємо:** `Payments` містить interfaces `PaymentGateway`, `ReceiptStore` та вісім concrete classes.

$$
A = \frac{2}{8 + 2} = 0.2
$$

**Читаємо результат:** два з десяти типів є абстракціями. `A = 0.2` означає 20% абстрактних типів, а не 20% абстрактного коду за кількістю рядків. Велика реалізація і маленький interface тут рахуються по одному типу.

**Що робити:** дивитися, чи захищають ці interfaces справді потрібні межі. Для пакета контрактів високе `A` природне; для модуля реалізації низьке `A` теж може бути нормальним.

### Instability

$$
I = \frac{C_e}{C_e + C_a}
$$

- $C_e$ - efferent/outgoing coupling: від скількох зовнішніх елементів залежить досліджуваний модуль;
- $C_a$ - afferent/incoming coupling: скільки зовнішніх елементів залежать від нього;
- `0` - structurally stable; `1` - structurally unstable.

**Рахуємо:** модуль залежить від трьох зовнішніх класів, а два зовнішні класи залежать від його типів. Тоді:

$$
I = \frac{3}{3 + 2} = \frac{3}{5} = 0.6
$$

Рахуємо різні залежні елементи за обраними правилами, а не кількість викликів за секунду. Якщо один клас викликано сто разів, це не сто різних класів-залежностей.

| `Ce` | `Ca` | `I` | Як читати |
|---|---|---|---|
| 0 | 10 | 0 | Зовнішніх залежностей немає, але десять споживачів обмежують свободу змін API |
| 3 | 2 | 0.6 | Є і залежності, і споживачі; жоден напрям не можна ігнорувати |
| 10 | 0 | 1 | Модуль залежить від інших, але в межах аналізу немає його споживачів |

**Що робити:** при високому `I` перевірити вплив змін у залежностях; при низькому - обережно змінювати API, який використовують інші. `I = 1` саме по собі не є дефектом, а `I = 0` не означає безвідмовність.

### Distance from the Main Sequence

$$
D = |A + I - 1|
$$

- `A` та `I` беремо для того самого модуля;
- `D = 0` - точка лежить на Main Sequence, де `A + I = 1`;
- що більше `D`, то більше відхилення від цієї лінії;
- high `A` + high `I` -> **Zone of Uselessness**;
- low `A` + low `I` -> **Zone of Pain**.

**Рахуємо:** беремо `A = 0.2` і `I = 0.6` з прикладів вище.

$$
D = |0.2 + 0.6 - 1| = |-0.2| = 0.2
$$

Риски `|…|` означають абсолютне значення: `|-0.2| = 0.2`. Знак показував би сторону від лінії, але для величини відхилення він не потрібний.

| `A` | `I` | `D` | Інтерпретація |
|---|---|---|---|
| 1 | 0 | 0 | Стабільні абстракції, наприклад пакет контрактів |
| 0 | 1 | 0 | Конкретна реалізація без зовнішніх споживачів у межах аналізу |
| 0.2 | 0.6 | 0.2 | Нижче Main Sequence: перевірити відповідність структури ролі модуля |
| 0.1 | 0.1 | 0.8 | Близько до Zone of Pain: мало абстракцій, багато відповідальності перед споживачами |
| 0.9 | 0.9 | 0.8 | Близько до Zone of Uselessness: багато абстракцій і залежності переважно назовні |

Однакове `D` у двох останніх рядках описує різні ситуації. Тому одного числа недостатньо: дивимося ще на `A`, `I` та призначення модуля. Не варто додавати штучні interfaces або залежності, щоб «підігнати» результат до нуля.

> [!note] Нормована та геометрична відстань
> Тут `D = |A + I - 1|` - **normalized distance**, яку Robert C. Martin також позначає `D′`. Геометрична відстань до прямої `A + I = 1` дорівнює `|A + I - 1| / √2`; для нашого прикладу це приблизно `0.141`. [Джерело уточнення: Design Principles and Design Patterns, pp. 31-33](https://objectmentor.com/resources/articles/Principles_and_Patterns.pdf#page=31).

### LCOM1 - підрахунок пар методів

Для варіанта LCOM із Chapter 3, Equation 3-1:

$$
LCOM_1 = \max(P - Q,\ 0)
$$

- $P$ - кількість пар методів, які **не мають** спільного поля;
- $Q$ - кількість пар методів, які **мають** хоча б одне спільне поле;
- `max(..., 0)` замінює від'ємний результат нулем.

**Рахуємо:** методи `m1`, `m2` використовують поле `profile`, а `m3`, `m4` - поле `report`. Інших звернень до полів у прикладі немає. Конструктори не включаємо в цей навчальний підрахунок.

| Пари методів | Спільний стан | Категорія |
|---|---|---|
| `(m1, m2)`, `(m3, m4)` | Є: `profile` або `report` | `Q = 2` |
| `(m1, m3)`, `(m1, m4)`, `(m2, m3)`, `(m2, m4)` | Немає | `P = 4` |

$$
LCOM_1 = \max(4 - 2,\ 0) = 2
$$

Це сигнал перевірити, чи не поєднано дві незалежні відповідальності. Якщо всі чотири методи використовували б спільне поле, отримали б `P = 0`, `Q = 6`, отже `LCOM1 = 0`. Але навіть спільний технічний об'єкт ще не доводить спільності бізнесового призначення.

LCOM має кілька варіантів із різними шкалами та правилами. Наш `LCOM1 = 2` не означає «два зайві класи» або «200% проблем»; його не слід напряму порівнювати з `LCOM96b` чи кількістю ізольованих груп. [Опис реалізації LCOM1 та інших варіантів: Aivosto](https://www.aivosto.com/project/help/pm-oo-cohesion.html).

### Крайові випадки та коротка вправа

Якщо `ma + mc = 0`, формула `A` має нульовий знаменник. Якщо `Ca + Ce = 0`, так само не визначено `I`. Для таких випадків перевіряємо домовленість конкретного інструмента; не підставляємо нуль мовчки. Якщо `A` або `I` не визначено, звичайний розрахунок `D` також неможливий.

**Спробуй сам:** модуль містить 1 interface та 4 concrete classes. Від нього залежать 8 зовнішніх класів, а він залежить від 2. Знайди `A`, `I` і `D` та поясни результат.

> [!tip]- Відповідь
> `A = 1 / (1 + 4) = 0.2`.
>
> `I = 2 / (2 + 8) = 0.2`.
>
> `D = |0.2 + 0.2 - 1| = 0.6`.
>
> Модуль досить concrete і structurally stable: зміна API може зачепити багатьох споживачів. Це привід вивчити його відповідальність і історію змін, а не автоматична вимога додати interfaces.

## Decision checklist

- Який **business driver** стоїть за рішенням?
- Які architecture characteristics справді критичні?
- Які є alternatives?
- Які benefits, costs і risks кожної?
- Які assumptions можуть змінитися?
- Чи не надто дрібна granularity?
- Чи висока cohesion усередині module?
- Який coupling перетинає boundaries?
- Чи можна замінити сильну connascence слабшою?
- Чи записано **why**, а не лише **how**?
- Як автоматично перевіряти compliance?
